# RP2040

## Debugprobe Firmware (formely Picoprobe)

Download 'debugprobe_on_pico.uf2' from [releases](https://github.com/raspberrypi/debugprobe/releases).

No drivers necessary on Windows 11, but for container development you will need [usbipd-win](https://learn.microsoft.com/en-us/windows/wsl/connect-usb):

```ps
winget install --interactive --exact dorssel.usbipd-win
```

Share the Debugprobe with WSL via:

```ps
# Older 'interface/picoprobe.cfg' is 2e8a:0004
# Newer 'interface/csmis-dap.cfp' is 2e8a:000c
sudo usbipd bind --hardware-id 2e8a:000c
usbipd attach --auto-attach --hardware-id 2e8a:000c --wsl
```

And add the following to your devcontainer.json:

```json
    "runArgs": [
        "--privileged",             // Required to access Picoprobe SWD from dev container
        "--device=/dev/ttyACM0"     // Expose Picoprobe URT to dev container
    ],
    
    // TODO: Figure out how to connect to Picoprobe as a non-root user.
    //       Maybe https://github.com/robotdad/piconotes?tab=readme-ov-file#setup-udev-rules-in-wsl?
    "remoteUser": "root"
```

## SWD firmware updates

With a CMSIS-DAP probe connected, run from the repository root:

```sh
cmake --preset default
cmake --build --preset prog
```

`prog` builds and programs bootloader, firmware and gateware.

For selective updates, replace `prog` with `prog-fw` (firmware and its ROM build
prerequisites), `prog-gw` (gateware), or `prog-boot` (bootloader).

### Notes

- A changed bootloader erases firmware vectors. Follow `prog-boot` with `prog-fw`,
  or use `prog` to restore firmware in the same session.
- Remove or rename SD-card `firmware.uf2` while debugging. A different valid file
  can replace SWD-loaded images on reset. The bootloader normally deletes processed
  files, but read-only files remain.
- Disconnect a JTAG programmer to load gateware from RP2040 flash. Firmware skips
  FPGA configuration while the programmer holds FPGA reset deasserted.
- Change partitions only in [FlashLayout.cmake](../../cmake/FlashLayout.cmake),
  then rebuild and deploy matching firmware and gateware.

### Image checks

After building the SD-card package, check firmware and combined-update layouts:

```sh
ctest --test-dir build -R '^(firmware|sdcard)_flash_layout$' --output-on-failure
```

## Notes

### Input routing and diagnostics

Shared input scheduling, actions, controls, routing, UART decoding, keyboard
ownership, and paced terminal injection live in `fw/src/input/`. USB transport
and PET matrix adapters remain in `fw/src/usb/`.

The input router is the sole destination selector. Adapters decode terminal
characters, USB key edges, physical PET matrix edges, and button gestures.
One shared TUI vocabulary (Up/Down, Page Up/Down, Activate, and Back) flows
through a source-tagged FIFO in observation order, before configurable PET
mapping. Menu bindings map Left/Right to paging and ignore Home/End.
Other typing, including T/t, is ignored while browsing. One router transition
cancels stale navigation, paced terminal input, and runtime matrix ownership.
USB adapters retain raw reports so held keys and modifiers cannot replay when
leaving the menu. The physical scanner baselines its observed matrix.
Physical PET input is limited to observed matrix snapshots, so taps absent from
all snapshots cannot be recovered.

The UART adapter owns byte acquisition, incremental CSI escape decoding, and
CRLF normalization. Partial sequences remain adapter-owned between input
iterations, with a 10 ms inter-byte timeout. A lone Escape is delivered on
timeout, while incomplete or unsupported CSI sequences are discarded with a
debug log. Supported suffixes must match exactly. No timeout loop holds up USB,
button sampling, paced typing, or FPGA synchronization. The router accepts one
decoded terminal key and binds its menu meaning only after selecting the menu.

Outside the menu, remote UART characters become paced key/modifier edges.
Once routed to paced injection, they feed the keyboard core directly, without
re-entering routing. USB adapters submit decoded batches through the router.
Each batch carries one source's modifier changes and key edges. The core
applies modifiers, releases, presses, and the final modifier update internally.
Both producers use the same source-owned core, without synthetic HID reports
or USB interface state. The core owns held keys, saved
press mappings, modifier arbitration, matrix-cell references, and source
cancellation. USB attachment, report history, and LED transport remain in the
USB adapter. CRLF is treated as one Enter in both runtime and menu input.

One `terminal_session_t` selects CLI or Remote and determines ordinary terminal
rendering and UART routing. It is independent of menu ownership. Fatal screens
render their final error window directly before entering the nonreturning
fatal loop. The CLI `log` command prints saved log entries but is not a terminal
session mode.
Ctrl+C exits Remote and cancels only terminal input, not machine requests.

System actions are separate typed requests, not navigation FIFO entries.
One router binding resolves recognized gestures using the current destination:

| Gesture | Running | Menu |
| --- | --- | --- |
| Short button press | Request Reset | Down |
| Long button press | Request Menu | Activate |
| Dual-Shift hold | Request Menu | Ignore |

Genuine machine requests survive release, source removal, input cancellation,
and storage delays until the machine controller consumes them. Simultaneous
observations coalesce, with the button taking priority.
The machine controller does not interpret button identity or menu navigation.
It leaves requests latched while SD is busy and returns to the main loop
without sleeping or servicing a special scheduling loop. Only when storage
is quiet does it consume a request and begin reset or menu entry. All normal
input, injection, FPGA synchronization, and drive tasks keep running during
the delay. Continued storage activity postpones the request, not input.
`input_task()` observes inputs and advances gesture timers. Queue reads only
read queues. Navigation cannot delay a system request.

Firmware tests compile the production `input_task()` and `sync_state()`.
Hardware fixtures supply UART bytes, USB reports, button GPIO levels, and
independent PET/CRTC snapshots. SPI writes record the published runtime matrix.
Orchestration tests verify acquisition order, passive queue reads, escape
fragmentation and timeouts, and continued matrix publication while storage
delays a machine request. Direct component tests still cover binding and source
ownership. Component menu fixtures emit actions during USB servicing after
rendering, never as a queue-read side effect. Physical hardware validation is
separate from these host checks.

The advanced CLI command `test` runs the existing continuous SRAM and character
BRAM diagnostic synchronously. The shared `pet_wait_for_storage_idle()` services
the IEEE drive until SD inactivity meets its threshold before the CLI halts the
CPU and enters the test. This synchronous wait is diagnostic-only, not used for
runtime menu/reset requests. It leaves CPU state unchanged and does not close
channels, flush caches, or guarantee an empty IEEE pipeline. The test repeats
until reset or a detected mismatch and overwrites the tested memory. There is
no confirmation or additional diagnostic banner.

## Oscillator

With a 1K resistor, YSX321SL requires XOSC workaround:

```cmake
# EconoPET 40/8096 Rev. A: xosc requires a little extra time to stabilize.
# On tested sample (45240-60), 8ms was intermittent and 16ms was reliable.
# 64ms provides a large tolerance.
target_compile_definitions(${PROJECT_NAME} PUBLIC PICO_XOSC_STARTUP_DELAY_MULTIPLIER=64)
```

Anecdotally, [this project](https://github.com/Swyter/psdaptwor/tree/master) claims that 100 ohm + 33pF is "known good".  (4-layer)
